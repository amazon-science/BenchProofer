A formally verified twin of real software-engineering tasks, and the pipeline that constructs one.

Summary

Coding agents are judged almost entirely by held-out tests. Tests are finite, so a patch that passes them can still be wrong on inputs nobody wrote a case for, and an agent optimising against them can satisfy the cases without fixing the defect. Formal verification answers the whole specified domain instead of a sample of it, but the verified-code-generation literature has largely stayed with self-contained exercises whose specification is given as part of the problem.

SWE-Proof attaches a machine-checked correctness oracle to real repository issues. For every instance it publishes a formal specification of the required change, axioms summarising the unchanged callees the fix depends on, a reference implementation that verifies against that specification, the equivalent repository patch, and the recorded outcome of every gate that admitted the instance. Scaling verification to a real repository rests on two ideas: model only the code the fix introduces, and summarise its interaction with everything it calls as axioms that are fuzzed against the real callees; then admit an instance only when a stack of mechanical checks and adversarial auditors has failed to refute it.

The claim a bundle makes

If an implementation satisfies an instance's formal specification and verifies under that instance's backend, then the corresponding repository patch resolves the instance under the official harness.

The property has two directions, and they fail differently. A specification that admits a wrong implementation makes a verified answer not a correct one. A specification that rejects a correct implementation makes the instance unsolvable by a faithful patch of a different shape. Every gate below attacks one of those directions, or protects an input the attacks depend on. Nothing is established by the party that produced it: each recorded outcome comes from a re-check performed afterwards by code that did not write the bundle.

Verification backends

Each instance is built independently under four backends. The spread is deliberate: it covers an imperative contract language, a proof assistant with automatic discharge, one with hand-written proofs, and a specification form with no prover at all, which is what forces the rest of the system to be written against an interface rather than against a single verifier.

BackendSpecification languageHow obligations are discharged
nagini statically typed Python with Nagini contracts automatic, through Viper to an SMT solver
velvet Velvet, an imperative DSL embedded in Lean 4 automatic, SMT-backed, checked by the Lean kernel
lean Lean 4 definitions with Mathlib proofs written by an agent, accepted only by the Lean kernel
ears structured natural-language EARS requirements no prover: structural lint plus an adversarial probe audit

What an instance contains

One instance is a frozen task record plus one bundle per backend. Every artifact below is published, so each step of the argument can be re-checked without rerunning the pipeline.

Specification
Pre- and postconditions for the changed behaviour, in the backend's language, together with the axioms and helper definitions the contracts use.
Axioms
One per unchanged callee the fix relies on, stating only the property it relies on. Axioms are the boundary between what is verified and what is assumed, and each ships with the tests that probe it against the real callee.
Reference implementation
A faithful skeleton of the real fix that verifies against the specification, with the proof annotations its backend needs.
Pre-fix twin
The same specification paired with the buggy implementation. It must fail to verify, which is what makes the specification non-vacuous.
Equivalent patch
The repository diff that applies at the base commit and resolves the issue, with a documented step-by-step correspondence to the reference implementation.
Property battery
Rival implementations with machine-checkable expected outcomes: admissibility probes that must verify, and near misses that must be refuted.
Gate record
Every verdict, stamped with the judging code's version and a digest of the bytes it judged, so a reader can tell which judge ran on what.

How an instance is admitted

Mechanical checks are necessary and not sufficient, so the rest of the suite is adversarial: model agents instructed to refute the instance by exhibiting a concrete counterexample. An instance is admitted only when every gate passes, and any counterexample sends it back for revision. Hover a gate name for the exact check it performs.

Reading a bundle

Two judgments the gates cannot make are left to a reader: whether a specification is faithful to the behaviour it models, and whether it discloses the fix. Both need the specification, the repository at the base commit, and the gate notes side by side, which is what the rest of this site is for.

  • Instance boards list every instance for one corpus and backend, with its gate verdicts at a glance and filters for the cells worth a second look.
  • An instance page carries the specification, the pre-fix twin and the diff between them, the patch, the property battery with each case's adjudicated outcome, the audit verdict in full, and the repository as it stood at the base commit.
  • The header chooser moves between corpora and backends, and keeps the instance you are reading when you change backend.

Reproducing, and porting to another benchmark

The construction pipeline is released with the corpora. Whether a corpus is releasable has one executable definition rather than a judgment:

python scripts/release_gate.py --benchmark-dir benchmark-verified

It is a conjunction of independent checks: every cell green, every stamp describing the bytes on disk, every audit still describing the specification it judged, every property battery importable, and no stale failure label. A cell it cannot measure counts as a failure rather than a pass.

Nothing in the construction loop, the gate suite, or the evaluation harness is specific to one dataset or one prover. Pointing the pipeline at a different benchmark is a registry entry, a row adapter if its records are not already the frozen schema, and an oracle adapter, none of which has to be an edit to the pipeline. Adding another specification language is one backend class. See the repository's docs/ for both seams.
