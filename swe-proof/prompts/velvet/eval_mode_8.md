Your task: from the issue and the code, CONSTRUCT a formal Velvet SPECIFICATION of the fix the issue requires, and a small implementation that VERIFIES under it. You are graded on the quality of the SPECIFICATION — not on editing the repository (any repo edits are ignored). Follow this order:
  (1) UNDERSTAND THE INTENDED BEHAVIOUR. Reproduce the issue's behaviour concretely (a small script, or the snippet from the problem statement) and trace it through the code, so you know exactly what the corrected behaviour must be — the real cases the fix distinguishes and the result in each, including the concrete details a test would observe (output values/strings, ordering, error conditions).
  (2) WRITE THE SPECIFICATION as `require`/`ensures` clauses on the method(s) the fix concerns, at whatever abstraction (strings as code-point lists, opaque handles, int-scaled values) lets you state the behaviour cleanly. Make it:
    - PERMISSIVE ENOUGH: the preconditions must admit every input the corrected code legitimately handles — do not exclude valid inputs to make the proof easier.
    - TRUE: every postcondition must be a correct statement about the intended behaviour — never assert something the correct fix would violate.
    - STRONG ENOUGH: the postconditions must pin the behaviour tightly enough that ONLY a correct implementation can satisfy them. A vacuous, trivially-true, or too-weak spec that a WRONG implementation (in particular, the current buggy behaviour the issue reports) could also satisfy is a failure. After writing it, ask yourself: could an incorrect implementation still verify against this? If yes, strengthen it.
  (3) For any UNCHANGED system or library function the behaviour depends on, you may add an `axiom` stating the property of that callee you rely on — but it must be TRUE of the real callee and must be the WEAKEST property you need. Do NOT axiomatize the behaviour the fix itself introduces (that would just assume the fix correct); the changed behaviour must be spelled out in the spec, not asserted as an axiom.
  (4) Write a small implementation under the spec and iterate with `velvet_verify` until it VERIFIES — this both forces the spec to be precise and confirms the spec is satisfiable (a spec nothing can satisfy is also a failure).
  (5) `submit` with model_path set to your specification file. The implementation only needs to verify; it is the SPECIFICATION that is judged.
